# 修理報告から修理事例（HP）・Google最新情報の下書きを作るしくみ（本番用）

1回の修理報告から、HPの修理事例とGoogle最新情報の下書きを作り、オーナーが承認したものだけを公開する。
このしくみ以前に作った修理事例（手作りの記事・一覧カード・画像）は変更しない。
記事・Google投稿の文章の書き方は [修理事例の記事作成ルール](case-writing-rules.md) に従う。

## 流れ（方法A：パソコン経由）

```
スタッフ：今のGoogleフォームで報告（変更なし）
  ↓ 読むだけ
承認画面（Apps Script・管理用スプレッドシートに付属。オーナー本人だけが操作できる）
  ① 最近の回答から1件選んで取り込む → 受け渡し用フォルダに報告と写真のコピーを置く
  ② 「材料と写真を1つのファイルにまとめる」→「材料セットをダウンロード」（またはコピー）でパソコンに渡す
     → node tools/cases/open-material.mjs --check（写真の確認・作業フォルダへ）→ 報告文だけを材料に下書きを作る
  ③ 下書きを承認画面に貼り付けて読み込む（ドライブの drafts フォルダからも読み込める）
     → 掲載日（記事のURLの日付）は読み込んだ日になる → 写真ごとに「公開OK／使わない」→ HP記事・Google投稿を確認して承認
  ④ HP記事を承認すると、公開候補と「公開セット」（公開候補＋公開OKの写真・SHA-256つき、1ファイル）を受け渡し用フォルダに置く
  ↓ 承認画面の「公開セットをダウンロード」（1ファイル）
パソコン（このリポジトリ）
  ⑤ 写真のプライバシー確認（AI）… 公開セットの写真を tools/cases/privacy-check.mjs で見て、
       顔・書類・QRコード・シリアル・画面などを確かめ、処理（塗りつぶし・ぼかし・切り抜き）か公開しないかを決める
       （記事作成ルールの「写真のプライバシー処理」。毎回オーナーに確認しなくてよい）
  ⑥ node tools/cases/run-approved.mjs --privacy <確認ファイル> --push … 次をまとめて行い、途中で問題があれば止める
       公開セットの確認（承認の指紋・写真の SHA-256・公開OKの写真だけ・写真のプライバシー確認）→ main から作業用ブランチ
       → 公開用の画像（prepare-approved.mjs）→ 記事・一覧・サイトマップ・公開記録（publish.mjs）
       → 予定外のファイルがないか・テストデータの確認（check-no-test-data.mjs）→ 作業用ブランチに記録
       → GitHub の作業用ブランチへ送り、Cloudflare のプレビューができるまで待って URL を表示（main には送らない）
       公開用の画像は、元の写真を変えずにコピーを処理して作り、処理した部分が読めないことを測って確かめる
       画質の補正（明るさ・色味・ノイズ・鮮明度・傾き）も行い、補正で悪くなる写真は補正しない
  ⑦ オーナーがプレビュー（処理した写真を含む）を確認 → 明確な承認 → main に統合して公開（main はPRが必要）
```

公開セットを作れなかったとき（写真が大きすぎるなど）は、承認画面に理由が出る。そのときは従来どおり
approved フォルダの公開候補と photos フォルダの写真をダウンロードし、prepare-approved.mjs・publish.mjs を順に使う。

Google最新情報は、承認状態を記録するだけで、投稿はまだ行わない。

## 公開しないもの・守るもの
- 未承認・差し戻し・承認取り消し・承認の後に内容が変わったもの（承認画面とHP側で同じ計算の「指紋」を比べる）
- 「公開OK」になっていない写真。使う写真は、縮小・WebP・一覧用（800×600）・Google用（1200×900）を作り、位置情報などの撮影情報は消える
- 同じ報告IDは二重に登録しない。新しい版で再承認されたものだけ更新し、古い版では上書きしない
- 手作りの公開済み記事と同じURL、別の報告と同じURL、既存の画像と同じファイル名（番号を付ける）
- テストデータは本番用に作らない
- リポジトリは誰でも見られるため、公開記録にはスタッフの報告文・確認メモ・メールアドレス・元写真のIDを残さない
- 結果は `content/case-reports/_logs/publish.jsonl` に残す

## Googleビジネスプロフィール（最新情報・写真一覧）

最新情報と写真一覧は**別々に承認・送信・記録**する（最新情報に写真を付けても、写真一覧に載ったことにはしない）。

| 対象 | 承認画面の承認 | 送るもの |
|---|---|---|
| 最新情報 | 「Google投稿」（HP記事の承認が先） | 本文・代表写真（HPに公開した1200×900の画像のURL）・「詳細」ボタン＝HP記事のURL |
| 写真一覧 | 「Google写真一覧」（HP記事の承認が先） | 「公開OK」の写真すべて（切り抜かず長辺2048px・高画質・分類「仕事風景」・説明＝alt） |

- 写真名：`地域-機種-修理内容-01.jpg`（2枚目は 02）。例 `mito-iphone-16-pro-charging-port-maintenance-01.jpg`。
  既存の画像と重なれば掲載日を入れる（`…-20261117-01.jpg`）。元の写真はGoogleドライブに残し、名前を付けたコピーを使う。
- 写真一覧用の画像は `prepare-approved.mjs --gbp-out <リポジトリの外のフォルダ>` で作る（HPには置かない）。
- 送信は `node tools/cases/gbp.mjs --candidates <公開候補> --state <リポジトリの外の記録フォルダ> --mode plan|mock`。
  - HP記事が公開済み（公開記録があり、承認した内容と同じ）でなければ何もしない
  - 承認の後に内容が変わったものは送らない。成功したものは二度送らない。失敗したものだけ次の実行で送り直す
  - 送信中のまま止まったものは自動で送り直さない（Google上で確認してから記録を直す）
  - 投稿ID・写真ID・成功／失敗・掲載の確認・日時を、記録フォルダの `<報告ID>.json` と `history.jsonl` に残す
  - `--mode live`（実際の投稿）は、API利用申請の承認とオーナーの承認まで使えない

## ファイル

| 場所 | 役割 |
|---|---|
| `tools/cases/lib.mjs` | 記事・一覧カード・Google投稿の作成、内容の確認、指紋 |
| `tools/cases/photos.mjs` `photo-process.js` `browser.mjs` | 写真の判定・ファイル名・画像処理（パソコンのEdgeで動かす） |
| `tools/cases/run-approved.mjs` | 公開セット1つから、作業用ブランチ・プレビューまでをまとめて行う |
| `tools/cases/privacy.mjs` `privacy-check.mjs` | 写真のプライバシー処理・仕上げ（確認ファイルの検査・確認用の画像） |
| `tools/cases/open-material.mjs` | 材料セット（材料＋写真）を開き、写真を確かめて作業フォルダに書き出す |
| `content/case-reports/photo-privacy/` | 公開した写真のプライバシー確認の記録（処理の範囲・方法・理由） |
| `tools/cases/prepare-approved.mjs` | 承認済みの写真から公開用の画像を作る |
| `tools/cases/publish.mjs` | 公開用データを作る（GitHubへの送信・公開はしない） |
| `tools/cases/gbp.mjs` | Google最新情報・写真一覧の送信の準備（今は表示・模擬だけ）と記録 |
| `tools/cases/check-no-test-data.mjs` | テスト用のものが混ざっていないかの確認 |
| `content/case-reports/published/` | このしくみで公開した修理事例の記録 |

記事ページの外枠（ヘッダー・お問い合わせ・店舗情報・フッター）は、公開済みの記事
`repair/cases/2026-11-13-mito-iphone13pro-screen-battery/index.html` をそのまま読み込んで使う。
